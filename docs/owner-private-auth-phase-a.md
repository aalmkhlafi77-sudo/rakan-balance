# RAKAN BALANCE — المرحلة A: المصادقة الخاصة بالمالك

الحالة: **أساس المصادقة فقط، غير جاهز للنشر العام**. المسار المعتمد: `rakan.carpetbazar.org` على Hostinger Business.

## القرار الهندسي المعتمد

- **زائر عام**: استعمال مباشر دون حساب، وحفظ خاص في IndexedDB على متصفحه.
- **المالك**: حساب واحد فقط، وكلمة مرور خاصة، وحفظ لاحق على MySQL مركزي بعد تنفيذ المرحلة B.
- كل المتطلبات المالية في المحرك الحالي باقية دون تعديل خلال المرحلة A.
- لا يُسمح بنقل أو قراءة البيانات المحلية تلقائيًا عند دخول المالك؛ النقل يكون لاحقًا بخطوة استيراد ومطابقة.
- **لا تسجيل حسابات عامة** ولا مزامنة مركزية للزوار.

## المنجز في المرحلة A

- واجهة Express تعمل على الخادم، منفصلة عن بناء React/Vite للواجهة.
- `owner_credentials` بسجل مالك وحيد (id=1) دون أي مسار تسجيل عام.
- تجزئة كلمة المرور باستخدام Node.js `scrypt` مع ملح عشوائي، ورفض كلمة مرور التهيئة الأقل من 14 حرفًا.
- جلسة عشوائية 256 بت، لا يُحفظ رمزها الخام في MySQL، بل بصمة SHA-256 فقط.
- Cookie للجلسة: `HttpOnly`، `SameSite=Strict`، `Path=/`، و`Secure` على HTTPS، دون Domain.
- جميع عمليات تغيير المصادقة تستخدم مطابقة `Origin` ورمز حماية CSRF؛ رفض المصادر الخارجية.
- تحديد محاولات الدخول على مستوى عملية الخادم (أساس مبدئي؛ **يستلزم حماية إضافية أمامية ودائمة** قبل النشر العام).
- عند خروج المالك تُبطل الجلسة في MySQL.
- `/api/owner/status` محمي ويرجع `storageReady:false` بصراحة؛ **لا توجد بعد نقطة نهاية للحسابات أو المرفقات أو المزامنة**.

## مسارات API في هذه المرحلة

| المسار | الوظيفة | الصلاحية |
|---|---|---|
| `GET /api/health` | اتصال خادم/قاعدة بيانات، دون بيانات حساسة | عام |
| `GET /api/auth/status` | حالة الجلسة، مع CSRF عند المصادقة | حسب الجلسة |
| `POST /api/auth/login` | مصادقة كلمة مرور المالك | محدود المحاولات |
| `POST /api/auth/logout` | إبطال الجلسة | مالك + Origin + CSRF |
| `GET /api/owner/status` | إثبات حارس المسار الخاص | مالك فقط |
| `/api/owner/*` الأخرى | غير موجودة حاليًا | 404، لا تُرجع بيانات |

## إعداد قاعدة Hostinger Business

1. أنشئ **قاعدة MySQL جديدة مستقلة** في حساب Business، ولا تستخدم أي قاعدة تخص موقعًا آخر.
2. شغّل نص `database/001_owner_auth.sql` على القاعدة الجديدة فقط.
3. اضبط قيم `DB_HOST` و`DB_PORT` و`DB_NAME` و`DB_USER` و`DB_PASSWORD` و`RAKAN_CSRF_SECRET` و`APP_ORIGIN` داخل أسرار التطبيق على الخادم. لا تستخدم بادئة `VITE_` لتلك الأسرار.
4. هيّئ كلمة مرور المالك **مرة واحدة فقط** بواسطة `npm run provision:owner` مع `RAKAN_OWNER_PASSWORD` داخل بيئة إدارة موثوقة؛ لا تضع كلمة المرور في المستودع أو أوامر shell المحفوظة أو السجلات.
5. أمر بناء الواجهة: `npm run build`. نقطة بدء الخادم بعد البناء: `server/start.mjs` (أو `npm start`). يحتاج هذا الوضع إلى نشر **تطبيق Node.js** بدل النشر الثابت الذي كان مقترحًا سابقًا.
6. لا تنشر المرحلة A منفردة للمستخدمين؛ واجهة الدخول والمزامنة وحماية التخزين/المرفقات لم تكتمل.

## تنظيف المعاينة والبيانات التجريبية — مطلب معتمد

**يجب إزالة عناصر «بيانات المعاينة» و«مساحة البيانات» وملفات بيانات العرض الافتراضية قبل النشر النهائي.**

جرد نقاط التنظيف الموجودة حاليًا:

- `src/components/Sidebar.tsx`: أزرار «البيانات الحقيقية» و«بيانات المعاينة» وشارة الوضع.
- `src/components/Navbar.tsx`: شريط تنبيه وضع المعاينة.
- `src/context/AppContext.tsx`: `switchScope`، `loadDemoData`، `purgeDemoData` وتهيئة بيانات العرض تلقائيًا.
- `src/storage/initial_data.ts`: `DEMO_ACCOUNTS` و`DEMO_TRANSACTIONS` و`DEMO_NOTES`. **احتفظ بتصنيفات `INITIAL_CATEGORIES` الأساسية، فهي ليست معاملات وهمية.**
- `src/storage/indexed_db.ts`: مخازن `STORES_DEMO` المعزولة.
- اختبارات N1/N2 والمتصفح تعتمد حاليًا على وضع المعاينة؛ **تُنقل بيانات الاختبارات إلى Fixtures مستقلة داخل بيئة الاختبار فقط** قبل إزالة مساحة المعاينة من التطبيق.

**ضمان عدم فقد البيانات:** لا تُحذف قاعدة `RakanBalanceDB_v2`، ولا تمس `STORES_REAL` ولا تُصفَّر LocalStorage أو نسخ الاحتياط. التعامل مع `STORES_DEMO` يتم بعد اختبار ترحيل الاختبارات وعدم المساس بأي بيانات فعلية قد أدخلها المستخدم خطأً في الوضع التجريبي؛ يجب إتاحة تصديرها أو تحذير واضح قبل حذفها.

## بوابات ما قبل النشر

A. نجاح اختبارات الخادم (كلمة المرور، الجلسات، Origin وCSRF، خروج المالك) واختبارات الواجهة والماليات الحالية.

B. طبقة تخزين MySQL للمالك مع صحة المراجع والحركات البينية ذرّيًا، والتحقق من إصدارات السجلات ومنع تعارض الأجهزة.

C. توصيل شاشة دخول المالك بالواجهة؛ منع تسريب بياناته إلى IndexedDB أو سجلات المتصفح بعد تسجيل الخروج.

D. نقل Fixtures وتنظيف المعاينة من واجهة الجمهور، ثم إثبات أن الزوار لا يتواصلون مع API الخاصة بالمالك عند العمل المعتاد.

E. تجربة دخول المالك على جهازين، واختبار انقطاع الاتصال والاستعادة والمرفقات والنسخ الاحتياطي.

F. نشر تجريبي مستقل مع SSL، وفحص الوصول غير المصرح به قبل أي إدخال لبيانات مالية حقيقية.
